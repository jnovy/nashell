## TIER 1: High Impact, Moderate Effort

### 1. Failed State Isolation (from Papers 1, 3)

**Problem:** When a tool call fails or an approach doesn't work, the failed
exchange stays in context at the same priority as successful ones. Paper 3
shows isolating failed steps prevents an 11.7% performance drop. Paper 1
shows experience anchoring to bad states causes negative transfer.

**Current state:** Nash has importance tiers (LOW/NORMAL/HIGH/CRITICAL) in
llm.h but no concept of "tainted" or "failed" messages. Error budget
tracking exists in react.c but doesn't affect message importance.

**Proposal:**
- Add `MSG_IMPORTANCE_TAINTED` level below LOW in llm.h
- When tool_execute() returns success=false, mark both the tool_call and
  tool_result messages as TAINTED
- In react_eviction.c, TAINTED messages get maximum eviction score -
  they're first to go during compaction
- In react_build_context(), if a TAINTED pair has been followed by a
  successful approach to the same goal, drop the TAINTED pair entirely
- Track consecutive failures: 3+ TAINTED exchanges on the same target
  triggers a "step back and reframe" prompt injection

**Hook points:**
- llm.h:79-83 (importance enum)
- react.c:1297 (after tool_execute, check tr.success)
- react_eviction.c (scoring formula, react_internal.h:26-30)
- react_error.c (consecutive failure tracking)

**Expected impact:** Cleaner context window, less confusion from failed
approaches, more reliable multi-step operations.

### 2. Typed Memory Edges (from Papers 1, 4)

**Problem:** Nash's refs[] links between memories are untyped strings. When
memory A supersedes memory B, the old one lingers and can still surface in
search results. No concept of CONTRADICTS or UPDATES relationships.

**Current state:** memory.h has refs[] (char** array), supersedes field, and
superseded_at timestamp. memory_query() gives a +0.5 score boost to
ref-linked entries. But refs carry no semantic type - a contradicting memory
gets the same boost as a supporting one.

**Proposal:**
- Add edge_type enum: `{MEM_EDGE_RELATED, MEM_EDGE_SUPERSEDES,
  MEM_EDGE_CONTRADICTS, MEM_EDGE_UPDATES}` to memory.h
- Extend refs[] to carry (key, edge_type) pairs instead of bare keys
- memory_query() scoring:
  - RELATED: +0.5 boost (current behavior)
  - SUPERSEDES: -1.0 penalty on the superseded entry (hard suppress)
  - CONTRADICTS: flag both entries for user attention, boost both
  - UPDATES: boost the newer entry, demote the older
- When storing with supersedes=X, automatically set edge_type=SUPERSEDES and
  mark X's status as superseded (close validity window per SodaMem)
- memory_search tool: add optional `edge_type` filter parameter
- Enforce that superseded entries never surface in auto-injection (pinned,
  triggers) unless explicitly searched

**Hook points:**
- memory.h:33-56 (mem_index_entry_t, add edge_type to refs)
- memory.h:247 (memory_set_supersedes - add edge creation)
- memory_query() scoring section
- tool_memory.c (memory_store handler - validate edges)

**Expected impact:** SodaMem achieves 92.8% accuracy largely because
superseded facts are EXCLUDED, not just demoted. This prevents stale
memories from polluting results.

### 3. Parallel Reasoning During Tool Waits (from Paper 2)

**Problem:** When Nash executes shell_exec, web_fetch, or subtask, the main
thread blocks waiting for the result. This idle time could run auxiliary
reasoning.

**Current state:** react.c:1297 calls tool_execute() synchronously.
subprocess.c already has async process support. Provider routing
infrastructure supports multiple providers.

**Proposal - Phase 1 (single "Alternative" branch):**
- When a tool is expected to take >2 seconds (shell_exec, web_fetch,
  subtask), fork a single background LLM call
- The background prompt: "While waiting for [tool] results, consider:
  What alternative approach would you take if this fails? What assumptions
  are you making that could be wrong?"
- Cap background generation at 200 tokens
- When the tool result arrives, append the background reasoning as a
  system note: "[Background thought: ...]"
- If tool succeeded, background thought is informational (LOW importance)
- If tool failed, background thought is promoted to NORMAL importance
  (the alternative approach becomes immediately useful)

**Proposal - Phase 2 (multi-branch):**
- Add Check (validate assumptions), Recall (query memory), Rehearse
  (pre-plan next steps) branches per the paper's taxonomy
- Recall branch directly calls memory_search during the wait
- Use atomic thought format: self-contained units that survive compaction

**Hook points:**
- react.c:1297 (fork background call before blocking tool_execute)
- react.c:1300+ (merge background result after tool returns)
- Provider routing: use reflection_provider or a dedicated cheap provider
  for background reasoning

**Expected impact:** Paper shows 10-43% reduction in main-thread decoding
tokens, 10.9% lower wall-clock latency, and up to +12.4 points on some
benchmarks. Even the single-branch variant (Alternative only) captures most
benefit at only 16-35% cost increase.

**Risk:** API cost increase. Mitigate by: (a) only triggering for tools
expected to take >2s, (b) using cheapest available provider, (c) making it
configurable (off by default).

## TIER 2: Medium Impact, Lower Effort

### 4. Memory Validity Lifecycle (from Papers 1, 4)

**Problem:** Memories accumulate indefinitely. Even with Bayesian validation
scoring, low-quality memories still appear in results. SodaMem shows that
hard temporal exclusion (validity gate) is critical.

**Current state:** Nash has validity field (persistent/volatile/session/
expires_when) and superseded_at timestamp. memory_prune() exists but relies
on validation score thresholds.

**Proposal:**
- Add explicit `status` field: `{ACTIVE, SUPERSEDED, INVALID, ARCHIVED}`
- memory_query() hard-excludes SUPERSEDED and INVALID entries (validity
  gate) - they simply don't appear in results
- Add `memory_invalidate(key, reason)` function callable from tool
- In react_post_loop(), when validation scoring finds memories with
  vscore < 0.2 after 10+ recalls, auto-mark as INVALID with reason
- Add `memory_search` parameter `include_invalid=true` for explicit
  archaeology (debugging why something was invalidated)
- Add temporal scoring bonus: memories accessed in the last 7 days get a
  recency boost; memories not accessed in 90 days get a staleness penalty

**Hook points:**
- memory.h (add status enum, modify mem_index_entry_t)
- memory_query() (add validity gate before scoring)
- react_reflection.c / react_post_loop (auto-invalidation)
- tool_memory.c (expose memory_invalidate as tool parameter)

### 5. Fix-to-Feature Monitoring (from Paper 5)

**Problem:** The PM4Py-UCM study shows fixes outnumber features 2.3:1 and
18% of turns correct agent errors. Without monitoring this ratio, Nash
can't detect when it's spiraling on corrections.

**Current state:** Journal tracks all tool actions. react.c has cycling
detection (FNV-1a hash signatures). But no higher-level pattern analysis.

**Proposal:**
- In journal entries, classify each step as one of: EXPLORE, IMPLEMENT,
  VERIFY, FIX, REFACTOR
- Classification heuristic:
  - FIX: file_edit after a failed shell_exec (compile/test error)
  - VERIFY: shell_exec of test/build commands
  - IMPLEMENT: file_edit/file_write not preceded by failure
  - EXPLORE: file_read, grep_search, glob_search
  - REFACTOR: file_edit when no failures and no new functionality
- Track rolling fix-to-feature ratio over last 10 steps
- When ratio exceeds 3:1, inject advisory: "Fix-to-feature ratio is high.
  Consider stepping back to reassess the approach rather than continuing
  to patch."
- Display ratio in TUI status bar or session summary

**Hook points:**
- journal.h (add step_class field to journal entries)
- react.c main loop (classify each step before journal_append)
- react_reflection.c (ratio analysis in post-loop)

### 6. Multi-Channel Memory Retrieval Fusion (from Papers 4, 6)

**Problem:** Nash's memory_query() blends semantic and substring scores
linearly. SodaMem shows connection-density fusion across 3 tunnels is
superior. SkillTrace shows MaxFusion (surface if ANY channel strongly
matches) prevents averaging-out of localized evidence.

**Current state:** memory_query() uses configurable blend: semantic_weight *
semantic_score + substring_weight * substring_score, plus recency bonus and
ref boosts.

**Proposal:**
- Add a third retrieval channel: graph traversal (follow refs[] edges from
  high-scoring entries, accumulate mass on connected entries)
- Change fusion from linear blend to connection-density:
  - Each channel votes independently (binary: above threshold or not)
  - Entries hit by multiple channels get multiplicative boost
  - MaxFusion override: if any single channel scores above "strong match"
    threshold (e.g., >0.9), entry surfaces regardless of other channels
- Calibrate thresholds using known-unrelated entries as negatives (per
  SkillTrace)

**Hook points:**
- memory_query() scoring pipeline
- memory.h recall tuning params (add graph_weight, fusion_mode)

## TIER 3: High Impact, High Effort (Future)

### 7. Transaction Boundaries for Tool Sequences (from Paper 3)

**Problem:** Multi-step operations (read file, edit, verify, commit) have no
atomicity. A failure mid-sequence leaves partial state.

**Proposal:**
- Define transaction as: exploration -> execution -> validation cycle
- Write-ahead action log: record intended actions before execution
- On validation failure: auto-rollback via git checkout or file restore
- Skill hubs: wrap common multi-step patterns as transactional units with
  built-in rollback
- This is architecturally significant - requires changes to react loop flow

**Prerequisite:** Failed state isolation (Proposal 1) should land first.

### 8. Operational Trace Memory (from Paper 6)

**Problem:** Nash memories store NL descriptions (expression trace) and
trigger patterns, but not the operational structure of multi-step workflows.
SkillTrace shows operational traces survive total rewrites and detect 73%
of reuse cases vs 31% for expression-only.

**Proposal:**
- At memory ingest time (memory_store of skills/strategies), use one LLM
  call to extract a Skill Operational Graph (SOG):
  - activation_conditions (when to apply)
  - procedure_steps [{action, object_role, tool_role, inputs, outputs}]
  - resource_dependencies (files, APIs, tools needed)
- Store SOG alongside NL value in memory entry
- At query time, match SOG deterministically (no LLM needed) using
  normalized action vocabulary (Nash's tool names are already a closed set)
- MaxFusion: surface memory if NL OR SOG OR trigger matches strongly

**Cost:** ~$0.01 per skill at ingest time (per SkillTrace measurements).
Query-time matching is free (deterministic).

### 9. Process Phase Diagnostics (from Paper 1)

**Problem:** Different tasks fail at different phases. CUDA tasks bottleneck
at Solution Framing (what to do), model development at Feedback Control
(using results effectively). A one-size-fits-all harness can't adapt.

**Proposal:**
- Tag each react loop step with phase: C1 (framing - exploring, planning),
  C2 (execution - editing, building), C3 (feedback - testing, iterating)
- In react_post_loop(), analyze phase distribution and success rates
- Inject phase-aware guidance:
  - Low C1 success: "Spend more time exploring before implementing"
  - Low C2 success: "Break implementation into smaller steps"
  - Low C3 success: "Add more verification steps; protect best state"
- Store phase profiles per task type in memory for cross-session learning

**Prerequisite:** Fix-to-feature monitoring (Proposal 5) provides the
classification infrastructure.
